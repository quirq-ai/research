## The question and context

qq is quirq's build, test and land system: 13 public infra repos modelled on
Chromium's infrastructure, used by two product repos, xo-space (Python) and
innernet (Next.js). This report answers, for v0: what each repo does and how
far it got, how a developer uses qq, what a product repo gets from it, how
policy and owners are configured, what is still limited, and what comes next.

## In one minute

- **What it is.** A repo-agnostic CI/CD system modelled on Chromium's. One
  config repo, infra-config, declares every repo, builder, gate rule and
  channel as TOML, and the tools that apply policy (gate, gardener, release,
  rollers, installer) read it at a pinned commit.
- **What a product repo gets.** Generated presubmit and post-submit workflows,
  a required check computed by the gate, stored test results, a gardener
  watching `main`, Dependabot and toolchain rolls, perf records, an `lkgr`
  pointer and a daily canary.
- **What works live.** `qq sync` fetches the promoted toolchains from public
  ghcr on a fresh GitHub runner every day; `lkgr` advances for both repos in
  release's `release-state` record; perf records `main` commits; gardener
  publishes tree status, and both trees are open.
- **What changed since 2026-10-04 21:15 UTC.** suraj's gate settings run
  happened (repo rulesets applied at gate `6610664`); suraj is named owner of
  the org and all 13 infra repos, and every infra repo's CODEOWNERS names him
  on its policy and trust paths; the infra-config `9123fa9` redelivery merged
  in both product repos (xo-space #220, innernet #44); innernet's first
  Dependabot roll (#43) merged.
- **What is left for v0.** suraj's open values (V0-CFG-04), the remaining
  owners (V0-ORG-02) and the owner-review rule that waits on them (V0-GAT-03),
  a settings re-apply that makes toolchains' promotion gate required, then the
  live validations: a red PR refused, the daily canary, an automatic revert.
  The gardener App and the release executor come after v0, designed with
  suraj.

## How a developer uses it

A developer, human or agent, writes code as usual and lets qq decide whether
it lands. The notes in italics say what is true on 2026-10-05.

1. **Set up once.** Clone depot and put its `bin` on `PATH` (the setup guide,
   [2026-10-05-qq-setup-depot-sync.md](2026-10-05-qq-setup-depot-sync.md),
   gives the exact commands). Inside a product repo, `qq` runs the version
   pinned in that repo's `infra/repo.toml`. *Both repos pin 0.1.0, which is
   depot `main`; another version needs a depot `v*` tag, and none exists.*
2. **Get toolchains.** `qq sync` (or `qq fetch <repo URL>` for a fresh clone)
   fetches every pinned toolchain from public ghcr, checks it against its
   digest and links it under `.qq/toolchains/`. *Live: depot's daily
   `e2e-sync` workflow does this for both product repos with no credentials.
   Toolchains exist for Linux x86_64 only, so on a Mac `qq sync` stops with
   "no pin for platform …" and you bring your own toolchain.*
3. **Build and test locally.** `qq build` and `qq test` hand the manifest to
   recipes and leave JUnit and `results.json` in `.qq/out`
   ([2026-10-05-qq-build-run-locally.md](2026-10-05-qq-build-run-locally.md)).
   *The generated CI builders still run interim commands, not recipes.*
4. **Open a PR.** `qq upload`, or a plain push and PR. The generated
   `<repo>-presubmit` check runs: a drift check that the `qq-*.yml` files were
   not hand-edited, then fetch, build and test, then the result sink, which
   stores every JUnit result in test-pipelines.
5. **Ask for a verdict.** `qq try` returns a run ID at once and pushes the
   verdict later to `$QQ_HOME/verdicts/` and an optional `--notify` command,
   so an agent never holds a tool call open. `qq status` gives it on demand:
   exit 0 pass, 1 refused, 3 pending.
6. **Land.** `qq land` asks the pinned gate for a verdict and only then queues
   the PR; the merge queue re-runs the same check on the exact merge result
   (`merge_group`) and squash-merges. *gate's README records that the repo
   rulesets, which carry the merge queue and required checks, were applied
   at gate `6610664`.*
7. **After it lands.** The post-submit builder runs on every `main` commit.
   gardener's cycle runs every 5 minutes and publishes tree status; if `main`
   goes red it groups the failure, finds the culprit and proposes a revert PR.
   *Reverts need the gardener App, which comes after v0; every revert is a
   proposal until a repo is in `auto_land_repos`.*
8. **Dependencies move.** Dependabot opens update PRs and `qq-roll-land`
   checks them; toolchain roll PRs come from the rollers App, quirqer.
   *Auto-land is off in v0, so a person merges every roll.*
9. **Ship.** release moves `lkgr` to the newest all-green `main` commit every
   10 minutes, and the daily canary (06:17 UTC) builds, tests, deploys and
   probes `lkgr` on a runner before moving `channels/canary`. *Live: `lkgr`
   points at both repos' current `main` in `release-state`. The canary's first
   scheduled run was 2026-10-05 06:17 UTC; no canary record had reached
   `release-state` when last checked. No git ref is written until the release
   executor exists.*
10. **Install from a channel.** `qqinstall resolve --repo xo-space --channel
    canary` reads `channels.json` and gives the commit and digest; xo-space
    test installs check out and verify exactly that. *It exits 3 (not
    published) until the first canary ships.*
11. **Measure.** perf records build size (innernet) and a benchmark (both
    repos) per `main` commit on its `perf-data` branch, as a record only,
    never a gate.

## Configuring policies and owners

Every policy is a TOML file in infra-config's `config/`, changed by a pull
request suraj approves. Repo settings are code in gate, applied with one
script.

**Where each kind of policy lives**

|---|---|---|

**How a policy change flows**

1. Edit `config/<area>.toml` in infra-config and open a PR. CI runs
   `qqcfg validate`: schemas, cross-file references, the invariants below, and
   that `generated/` is up to date (`qqcfg generate`).
2. suraj approves: infra-config's CODEOWNERS names him on `config/`,
   `schema/`, `tools/`, `generated/`, `tests/` and `.github/`. Squash-merge.
3. If the change touches generated workflows, `qqcfg deliver <repo>` writes
   them into a checkout of the product repo, which is opened as a PR; the drift
   check fails any hand edit.
4. Each tool repo reads infra-config at the commit pinned in its own
   `pins.toml` (gate, gardener, release, installer; rollers uses
   `infra-config.commit`), so a tool sees the change only after its pin is
   bumped.
5. Repo settings change through gate: edit `settings/github.toml`, merge, then
   an org owner with `gh` logged in runs one command from the gate commit they
   are given:

   ```sh
   ( mkdir -p ~/qq-apply && cd ~/qq-apply && rm -rf qq-gate && git clone -q https://github.com/quirq-ai/gate qq-gate && cd ./qq-gate && git checkout -q <COMMIT> && scripts/apply.sh )
   ```

   It shows a dry run, writes only what is approved at its prompts, and is
   safe to re-run ([gate `docs/apply-settings.md`](https://github.com/quirq-ai/gate/blob/c3721365186a35c4b2b5acdc0635e281e754ac13/docs/apply-settings.md)).

**Rules config cannot loosen.** These live in `tools/qqcfg.py`, itself a
policy path: stable promotion needs the policy-owner; canary is agents-only;
agents may land alone only clean reverts, dependency rolls and docs; at most 10
auto-reverts per rolling 24 hours; builders that run PR code get no secrets;
repos are public only. Source: [`tools/qqcfg.py`](https://github.com/quirq-ai/infra-config/blob/310e3264f5de3cd9822b3a4712ae0a372b97dac3/tools/qqcfg.py).

## Owners and bots

- **People.** suraj is the policy-owner (`org.toml [roles]`). Since
  infra-config `310e326`, the org area and all 13 infra repos list him as
  owner, and every infra repo's CODEOWNERS names him on its policy and trust
  paths only, with no catch-all, so other changes merge on green CI and
  review. The owners lists of the other 12 config areas and of both product
  repos in `repos.toml` are still empty; `qqcfg validate` lists them.
- **One owner is not enough.** GitHub does not let a PR's author approve it,
  so suraj's own PRs on owned paths need a second owner or a bot identity.
  Agent work in these repos is authored as `quirq-gates` (see the git logs),
  and suraj can approve those PRs. gate's README records this as a known
  conflict for suraj to settle.
- **Bots.** One GitHub App per tool. Live: quirqer (rollers). After v0,
  designed with suraj: the gardener App and the release executor.
- **What agents may do alone.** Land clean reverts, dependency rolls and docs,
  and promote to canary, within the caps above.

## Naming conventions

A repo's name says its area, its description says its job, and an org
property says which bot owns it. An adopted plan (vision/org/naming.md, not
public), not something any repo enforces.

| Thing | Convention | Examples |
|---|---|---|
| Product repo | its brand name; a separable part is `<product>-<part>` | `xo-space`, `innernet` |
| One-repo area | the area word | `docs`, `research` |
| Repo in a multi-repo area | `<area>-<thing>` | new infra repos: `infra-<thing>` |
| The 13 infra repos | keep their names for v0; `infra-*` is a later, optional migration | `gate`, `release` |
| Area and owner | org custom properties `area`, `owner-bot`, `owner`, `stage`; select repos by property, never by name | `area = infra` |
| Bots | one GitHub App per tool or area, named `quirq-<repo or area>` | `quirq-gardener`; rollers keeps quirqer |
| qq's own files | the `qq` prefix | `qq` CLI, `.qq/`, `qq-<repo>-presubmit.yml` |
| Builders and checks | `<repo>-<pipeline>`; the job name is the required check | `xo-space-presubmit` |
| Work items | `V<version>-<AREA>-<nn>` | `V0-GAT-01` |
| Release refs | `lkgr` and `channels/<channel>` | `channels/canary` |

Source: quirq-ai org naming, vision/org/naming.md (project files, not public,
adopted 2026-10-04).

## Adding a new repo

Onboarding a repo in a language qq already knows is two PRs plus a settings
run, with no code change in any tool repo. The repo must be public in quirq-ai
and use kinds recipes has adapters for: `python-service`, `pytest` and
`node-app`.

| Where | Change | Who approves |
|---|---|---|
| infra-config `config/repos.toml` | one `[[repo]]` block: source, kinds, manifest path, channels, owners, deploy target | suraj (policy path) |
| infra-config `config/pipelines.toml` | a blocking presubmit on `change` and `queue`, a post-submit mirror and, if it ships on canary, a canary release builder; `qqcfg validate` refuses a repo without them | suraj |
| infra-config `rollers.toml`, `perf.toml` | optional: Dependabot rollers, the toolchain rotation, a benchmark | suraj |
| the new repo | `infra/repo.toml` (checked with `qqsync validate`), the workflows from `qqcfg deliver`, and rollers' Dependabot files | the repo's owner |
| gate `settings/github.toml` | a `[[repo]]` entry, then the apply command above | suraj |
| GitHub | add the repo to the gardener and rollers App installations; turn on Dependabot | suraj (admin) |

What follows by itself once the tool repos bump their infra-config pin: the
required checks, tree status and channels. Still a hand edit: test-pipelines'
scorecard workflow and perf's workflow name xo-space and innernet directly. A
new language adds a kind in `kinds.toml`, one recipes adapter and one
toolchains build; core repos do not change, and gate's agnosticism guard fails
any core file that names a language.

## Limitations

| Limitation | Effect today | What clears it |
|---|---|---|
| Enforcement is not proven live | The repo rulesets are recorded as applied, but no red-PR refusal is recorded, and org rulesets (the pinned org presubmits, `qq-drift`) are off on GitHub Free | The red-PR validation in each product repo |
| `promotion-gate` not yet required | toolchains' promotion check is advisory until the settings are re-applied from gate `c372136` | A settings re-apply |
| No gardener App or release executor | gardener opens no reverts; release writes no `lkgr` or `channels/*` git refs; no depot `v*` tag can be cut | Per-tool bots, designed with suraj after v0 |
| Owners only partly named | The other config areas and the product repos have no owners; GAT-03 cannot start; suraj cannot approve his own PRs | suraj names more owners, or a bot identity |
| CI does not use qq's own parts yet | Generated builders use `setup-python`/`setup-node` and interim commands, not recipes or promoted pins; retry-then-compare is off | v1: builder steps move to recipes and `qq sync` |
| Nothing lands on its own | `auto_land_repos` is empty; Dependabot and toolchain auto-land are off | Reverts: an `auto_land_repos` change. Rolls: a gate PR and a settings run |
| Canary not proven live | The first scheduled canary was 2026-10-05 06:17 UTC; its result is not recorded yet; installs resolve nothing until it ships | The canary validation, then canary test machines |
| Signals are thin | perf takes one measurement per commit on shared runners, with no baseline; PostHog is v1 | v1 |
| Hand-kept lists | The scorecard and perf workflows name xo-space and innernet directly | A one-line PR per new repo |
| Narrow platform | GitHub only; toolchains for linux-x86_64 only | Launchpad (v2); more platforms |
| suraj's open values | Canary hour, how the revert cap counts, monthly compute ceiling | suraj sets them |

All 13 infra repos are licensed Apache-2.0.

## What's next

**To close v0:** suraj's values (CFG-04) and the remaining owners (ORG-02,
which unblocks GAT-03); a settings re-apply for `promotion-gate`; then the
live validations: a red PR refused in each product repo; 7 daily canaries
with no human touch, a held bad canary and a rollback drill; a planted break
reverted automatically.

**After v0:** per-tool GitHub Apps (the gardener App and the release
executor); builders switch to recipes and promoted toolchains; agents land
rolls and reverts alone, within caps; a one-command, fully idempotent setup
(planned as V1-ORG-01). See [2026-10-05-qq-phases.md](2026-10-05-qq-phases.md)
for v1 and v2.
