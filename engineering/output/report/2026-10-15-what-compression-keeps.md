# What Compression Keeps

Compression keeps every bit of information and spends fewer bits on it. Compaction keeps only the present and lets the past go. This is a long explainer of the first — entropy, models and coders, the LZ family, the codecs that matter in October 2026, the prediction contests at the frontier, lossy coding, compression on the wire and as an attack — and of the second in all its senses, from LSM trees and Kafka to garbage collectors, git and an agent's context window, measured where a machine can measure it, and compared side by side.

## 01 · Fewer bits, or fewer things

Compression and compaction make two different promises. Compression keeps all the information and spends fewer bits on it. Compaction keeps only what a reader can still observe, the present state, and rewrites it densely. Lossless compression can be undone. Compaction, as a rule, cannot.

In lossless compression a model predicts each symbol, a coder spends bits on the model's surprise, and the decoder runs the same model to get every byte back ([Information is surprise](#02-information-is-surprise), [A model and a coder](#03-a-model-and-a-coder)). Lossy compression keeps what a perceptual model says a person will notice, and its decoder returns a close copy ([Throwing away what nobody sees](#07-throwing-away-what-nobody-sees)). Neither drops anything for being old. *\[reconstruction\]*

Compaction does. The Raft paper describes log cleaning and log-structured merge (LSM) trees this way: "They first select a region of data that has accumulated many deleted and overwritten objects, then they rewrite the live objects from that region more compactly and free the region." (Ongaro and Ousterhout, "In Search of an Understandable Consensus Algorithm", extended version of the USENIX ATC 2014 paper, §7) *\[from the paper\]* What is freed is what no reader can observe: superseded versions, expired tombstones (records that mark a key deleted), dead tuples, unreachable objects ([Compaction: keeping only the present](#10-compaction-keeping-only-the-present)). None of it comes back. Some compactions only move live data and drop nothing; [Compression and compaction, side by side](#12-compression-and-compaction-side-by-side) sorts them. *\[reconstruction\]* KurrentDB's docs say so of its scavenge: "Once a scavenge has run, you cannot recover any deleted events except from a backup" (v26.0, "Scavenging"). *\[from the docs\]*

The words have traded places before. Visvalingam's 1976 paper "Indexing with coded deltas—a data compaction technique" (*Software: Practice and Experience* 6(3)) describes coded deltas "for compacting the 1971 U.K. census data": compression, in today's words. The UNIX `compact` utility was an adaptive Huffman coder (Lelewer and Hirschberg, "Data Compression", *ACM Computing Surveys* 19(3), 1987). *\[from the paper\]* The other way round, the log-structured file system's segment cleaner "regenerates empty segments by compressing the live data from heavily fragmented segments" (Rosenblum and Ousterhout, "The Design and Implementation of a Log-Structured File System", SOSP 1991). *\[from the paper\]* This post keeps the later, cleaner split, and Figure 1 draws it. *\[reconstruction\]*

### The answer, up front

Each item is my judgement. *\[reconstruction\]*

1.  **Compress when every byte or frame must survive and you want it smaller**: files at rest, bytes on the wire. Go lossy only for media, where a perceptual model may choose what is lost. Per-format recipes are in [What Each File Wants](2026-10-15-what-each-file-wants.md#01-every-file-wants-something-different).
2.  **Compact when old versions have no reader**: LSM stores, Kafka changelog topics, PostgreSQL and SQLite tables (`VACUUM`), garbage-collected heaps. If anyone may ask for the past, keep it elsewhere first.
3.  **When you do both, compact first and compress what is left**, as in Figure 2. Some tools do both in one command: git's manual (`Documentation/git-gc.adoc`, DESCRIPTION) lists "compressing file revisions" and "removing unreachable objects" among its tasks. *\[from the docs\]*
4.  **An agent's context is compacted when it fills, but its past may still have a reader**: keep the transcript beside the summary ([Compacting a conversation](#11-compacting-a-conversation)).

How storage engines hold JSON is the subject of [Where the JSON Lives](2026-10-15-where-the-json-lives.md).

## 02 · Information is surprise

Information is measured as surprise: an outcome of probability p costs log₂(1/p) bits, and entropy is the average. It is the floor for a lossless code under a model, not under the data. No lossless code shrinks every input.

Claude Shannon's "A Mathematical Theory of Communication" (Bell System Technical Journal vol. 27, July and October 1948) sets meaning aside: "These semantic aspects of communication are irrelevant to the engineering problem." *\[from the paper\]* Theorem 2 (§6) derives the measure from three requirements: "We shall call H = −Σ p_(i) log p_(i) the entropy of the set of probabilities p₁, …, p_(n)." Shannon called the theorem and its assumptions "in no way necessary for the present theory"; what justifies H is what it implies. *\[from the paper\]*

A fair coin carries 1 bit per toss. One that lands heads nine times in ten carries H(0.9) = −0.9 log₂ 0.9 − 0.1 log₂ 0.1 = 0.469 bits, so 1,000 tosses hold about 469 bits; at 99 in 100 it is 0.081 (Figure 3, panel A). Spending under a bit per toss takes a coder that does not round each toss to whole bits ([A model and a coder](#03-a-model-and-a-coder)). *\[reconstruction\]*

Theorem 3 splits long sequences into a set of negligible probability and a remainder whose per-symbol log-probability is close to H; after Theorem 4, Shannon concludes one may "treat the long sequences as though there were just 2^(HN) of them, each with a probability 2^(−HN)" (§7). *\[from the paper\]* Numbering them takes HN bits, so H per symbol is the floor. *\[reconstruction\]* Theorem 9 makes H the limit: over a channel of C bits per second, any rate below C/H symbols per second is reachable, and "It is not possible to transmit at an average rate greater than C/H." *\[from the paper\]*

In "Prediction and Entropy of Printed English" (BSTJ vol. 30 no. 1, January 1951), Shannon put English at "roughly 2.3 bits per letter" from statistics spanning at most eight letters, and at "something of the order of one bit per letter" once people guessing the next letter saw up to 100 letters. *\[from the paper\]*

### Entropy belongs to a model

H assumes known probabilities; a compressor must supply them. The simplest model is the file's own byte histogram; its entropy, order 0, bounds a coder that codes each byte alone. *\[reconstruction\]* Every structured file here goes well below it (Figure 3, panel B). Dickens's novels, 10,192,446 bytes of the Silesia benchmark corpus (twelve files, 211,938,580 bytes; Figure 10), have an order-0 entropy of 4.53 bits per byte; gzip -9 reaches 3.03 and bzip2 -9 2.20. For this site's `what-the-parser-hears/_numbers.json`, order 0 sets a floor of 518,267 × 4.7604 ÷ 8 ≈ 308,395 bytes; xz -9 writes 35,532, 8.7 times smaller. *\[measured here\]* Conditioning on the previous two bytes lowers Dickens to 2.80, with 4,030 samples per context. *\[measured here\]* Each richer model lowers the floor. *\[reconstruction\]*

The end of that road is the shortest program: Kolmogorov's "Three Approaches to the Quantitative Definition of Information" (Problems of Information Transmission, 1965, no. 1). ### Nothing shrinks everything

The comp.compression FAQ (§9.2, "The counting argument") proves the other limit. There are 2^(N) files of exactly N bits and only 2^(N) − 1 shorter ones, so "if a lossless compression program compresses some files, it must expand others, *regardless* of the compression method". *\[from the docs\]* Mahoney's *Data Compression Explained* bounds the fraction compressible from n bits to m bits by 2^(m − n): "less than 0.4% of strings can be compressed by one byte." *\[from the paper\]*

A stored mode caps the growth: RFC 1951 §1.1 gives DEFLATE's worst case as "5 bytes per 32K-byte block". *\[from the spec\]* On 1,048,576 pseudo-random bytes every codec grows the input (Figure 4): brotli by 5 bytes, zstd 33, raw DEFLATE 320, gzip 338, bzip2 5,181 (0.49%). *\[measured here\]* zstd's 33 is eight 3-byte raw-block headers (RFC 8878 §3.1.1.2), a 4-byte magic number and a 5-byte frame header (§3.1.1); DEFLATE's 320 is zlib's 64 stored blocks of 16 KiB at 5 bytes each; gzip adds an 18-byte wrapper (RFC 1952 §2.3). bzip2 has no stored mode. *\[reconstruction\]*

A compressor's work is finding a model under which the data is unsurprising. *\[reconstruction\]*

## 03 · A model and a coder

Every lossless compressor has two parts. A model gives each possible next symbol a probability; a coder spends about log₂(1/p) bits on the symbol that arrives. The best coders spend within one bit of that sum over a whole message, so the model is what separates compressors.

Rissanen and Langdon's "Universal modeling and coding" (IEEE Transactions on Information Theory 27(1), January 1981) made the split formal. *\[from the paper\]* Witten, Neal and Cleary's "Arithmetic coding for data compression" (Communications of the ACM 30(6), June 1987) priced it: "This separation of function costs nothing in compression performance, since arithmetic coding is (practically) optimal with respect to the entropy of the model." *\[from the paper\]* Mahoney's *Data Compression Explained* (§1.5): "Coding is a solved problem. Modeling is provably not solvable." *\[from the paper\]*

### Huffman: whole bits

David Huffman's "A Method for the Construction of Minimum-Redundancy Codes" (Proceedings of the IRE 40(9), September 1952) minimises "the average number of coding digits per message". *\[from the paper\]* It is optimal among prefix codes for known frequencies (RFC 1951 §3.2.1). *\[from the spec\]* Its lengths are whole bits: "If a symbol probability is not a power of 1/2, then the code assignment is less than optimal", and a two-symbol alphabet gets no compression without blocking (Mahoney, §3.1–3.2). *\[from the paper\]* The nine-in-ten coin of [Information is surprise](#02-information-is-surprise) carries 0.469 bits a toss; Huffman spends 1. *\[reconstruction\]*

### Arithmetic coding: one number for the message

Witten, Neal and Cleary trace arithmetic coding to Elias in the early 1960s, made practical in 1976 by Rissanen ("Generalized Kraft Inequality and Arithmetic Coding", IBM Journal of Research and Development 20(3)) and by Pasco's Stanford thesis. *\[from the paper\]* The coder keeps an interval, starting at \[0, 1); each symbol keeps its own slice, sized by its probability. The final width is the product of the probabilities, so naming a point inside costs about −log₂ of it. *\[reconstruction\]* A binary number that does so "can always be found that is no more than 1 bit longer than the Shannon limit" (Mahoney, §3.2). *\[from the paper\]*

Figure 5 codes A A B A both ways: 4 bits against Huffman's 5. Over a long run Huffman spends 0.8 × 1 + 0.2 × 2 = 1.2 bits a symbol; the entropy is 0.884. *\[reconstruction\]*

Range coding is the same machine with larger digits: G. N. N. Martin, "Range encoding: an algorithm for removing redundancy from a digitised message", for the Video & Data Recording Conference, Southampton, July 1979. *\[from the paper\]* RFC 6716 §4.1 (Opus) calls it "a rediscovery of the FIFO arithmetic code introduced by \[CODING-THESIS\]", Pasco's thesis, working "with digits in any base instead of with bits". *\[from the spec\]*

### ANS: one number as the state

Jarek Duda's asymmetric numeral systems (arXiv:0902.0271, 2009; arXiv:1311.2540, 2013) match that precision with a "single natural number as the state, instead of two to represent a range"; rANS, the range variant, needs one multiplication per step where range coding needs two, and tANS, the tabled variant, swaps the arithmetic for a table. *\[from the paper\]* Zstandard runs both families: "Huffman is used to compress literals, while FSE is used for all other symbols" (RFC 8878 §4). *\[from the spec\]* Its FSE, by Yann Collet, is tANS. *\[reconstruction\]* Collet's README shows the trade: on a skewed file FSE reaches ratio 8.84 to 6.38 for his Huffman coder, Huff0, which decodes at 1,350 MB/s to FSE's 440 (his figures). *\[from the docs\]* Google's ANS application US 2017/0164007 A1 shows as abandoned on Google Patents, a status that "is an assumption and is not a legal conclusion". *\[from the docs\]*

### Where each coder ships

AV1 does not use ANS. Its specification codes "An arithmetic encoded symbol coded from a small alphabet of at most 16 entries" against a CDF that adapts "to the content of the stream" (AV1 Bitstream & Decoding Process Specification, §4.10.9, §8.2.6). *\[from the spec\]* libaom's `aom_dsp/entdec.c` calls itself a range decoder after Martin and Pasco (lines 16–18), and `aom_dsp/` holds no ANS files. libvpx did carry an ANS coder: Draco's `ans.h` is "based off libvpx's ans.h" (line 19). *\[from the docs\]*

H.264's CABAC, adaptive binary arithmetic coding with context modelling, saves an average 9–14% of the bit rate on broadcast test material over the standard's baseline entropy coder (Marpe, Schwarz and Wiegand, "Context-based adaptive binary arithmetic coding in the H.264/AVC video compression standard", IEEE Transactions on Circuits and Systems for Video Technology, July 2003). *\[from the paper\]* Output this close to its model's entropy leaves gzip nothing to find in a video file ([Already compressed: leave it](2026-10-15-what-each-file-wants.md#12-already-compressed-leave-it)). *\[reconstruction\]* Figure 6 places each family.

With a fractional-bit coder, the rest is modelling: in high-end compressors "CPU time and memory are dominated by the model" (Mahoney, §3.3). *\[from the paper\]* The cheapest model is repetition ([Saying it again, by reference](#04-saying-it-again-by-reference)); the dearest is a neural network ([Compression is prediction](#06-compression-is-prediction)). *\[reconstruction\]*

## 04 · Saying it again, by reference

The other half of a practical compressor models repetition: a repeat is sent as a pointer to an earlier copy, a distance and a length. A pointer reaches only as far back as the window; a dictionary is a past both ends hold before the first byte.

Ziv and Lempel's "A universal algorithm for sequential data compression" (IEEE Transactions on Information Theory 23(3), May 1977) and "Compression of individual sequences via variable-rate coding" (24(5), September 1978) are the roots. *\[from the paper\]* LZ77 codes repeats "by offset and length of previous occurrence"; LZW, of the 1978 line, "as indexes into a dynamically built dictionary" (Large Text Compression Benchmark). *\[from the docs\]* Storer and Szymanski's "Data compression via textual substitution" (J. ACM 29(4), October 1982) gave a general model of macro schemes, which replace repeats "by pointers to a common copy". *\[from the paper\]* The program usually called LZSS is Haruhiko Okumura's 1988 sliding-window coder. *\[from the docs\]*

DEFLATE is LZ77 plus Huffman coding ([A model and a coder](#03-a-model-and-a-coder)), and RFC 1951 "limits distances to 32K bytes and lengths to 258 bytes" (§2). *\[from the spec\]* Figure 7 parses part of Shannon's own sentence within those limits: 92 bytes become 72 literal bytes and 5 matches covering 20 bytes, and zlib -9 writes 70 bytes of raw DEFLATE. A minified `posts.json` record reuses `_numbers.json`, 13 bytes, from 46 bytes back. *\[measured here\]*

Terry Welch's LZW, "A Technique for High-Performance Data Compression" (IEEE Computer 17(6), June 1984), builds its table as it goes; in his patent's words the decoder "generates a string table similar to that constructed by the compressor", so the table is never sent. *\[from the docs\]* US patent 4,558,302, filed by Sperry, later Unisys, on 20 June 1983, was granted on 10 December 1985. GIF used LZW. Unisys and CompuServe completed a licence on 21 June 1994; CompuServe's advisory to GIF developers followed in late December 1994 (sources disagree on the day). The first PNG draft was posted on 4 January 1995. The US patent expired on 20 June 2003, its last counterpart, Canada's, on 7 July 2004. *\[from the docs\]*

### Reach

A pointer cannot reach past the window: 32 KiB in DEFLATE (RFC 1951 §2), at most 16 MiB minus 16 bytes in Brotli (RFC 7932 §2), up to 3.75 TB in zstd's format (RFC 8878 §3.1.1.1.2), but 8 MB for zstd over HTTP (RFC 9659; [Compression on the wire](#08-compression-on-the-wire)). *\[from the spec\]* zstd's `--long` turns on long-distance matching (LDM) with a 128 MiB window by default. *\[from the docs\]*

### Sorting and predicting instead

Burrows and Wheeler's "A Block-sorting Lossless Data Compression Algorithm" (DEC SRC Research Report 124, 10 May 1994) sorts a block's rotations and keeps the last column: "The transformation does not itself compress the data, but reorders it to make it easy to compress". Wheeler found it in 1983. *\[from the paper\]* bzip2 pairs it with Huffman coding. *\[from the docs\]* Against gzip -9, zstd -19 and xz -9, bzip2 -9 is smallest on Dickens (2,799,520 bytes; xz -9 2,830,604), on this site's prose and on the JSON Lines log, and loses to xz -9 on JSON, Python source and the ELF binary. *\[measured here\]*

PPM predicts from the longest context seen and escapes to shorter ones for unseen bytes. *\[from the docs\]* Cleary and Witten's "Data Compression Using Adaptive Coding and Partial String Matching" (IEEE Transactions on Communications 32(4), 1984) coded mixed-case English in as little as 2.2 bits per character "with no prior knowledge of the source". *\[from the paper\]* Context mixing, from PAQ1 (6 January 2002) to cmix, combines many models' bit predictions; often, Matt Mahoney writes, "the combined prediction of independent models compresses better than any of the individuals that contributed to it". *\[from the docs\]* Its records are in [Compression is prediction](#06-compression-is-prediction).

### Repetition you already sent

Any bytes, at least 8, can serve zstd as a dictionary, a "past" in front of the data (RFC 8878 §5). *\[from the spec\]* `zstd --train` should ideally get over 100 samples weighing about 100 times the dictionary, whose default maximum is 112,640 bytes. *\[from the docs\]* Brotli ships one: 122,784 bytes, reached by distances beyond the window, each word in one of 121 forms (RFC 7932 §8). *\[from the spec\]* Decoded, its 13,504 words are 10,749 pure ASCII, most others CJK, Devanagari, Cyrillic or Arabic, and about 1,042 with HTML, CSS or JavaScript: multilingual web text, not markup. *\[reconstruction\]* Trained dictionaries are measured in [Small messages and dictionaries](2026-10-15-what-each-file-wants.md#04-small-messages-and-dictionaries); RFC 9842 negotiates them over HTTP ([Compression on the wire](#08-compression-on-the-wire)). *\[from the spec\]*

## 05 · The codecs that matter in 2026

The general-purpose lossless formats are old and fixed; their libraries are not. A level picks a point among ratio, compression speed and decompression speed. On Silesia, three settings make the frontier, zstd 1, zstd 9 and xz -9; zstd's default sits at its edge, and Brotli's and zlib's defaults sit off it. *\[measured here\]*

DEFLATE (RFC 1951) and its wrappers, zlib (RFC 1950) and gzip (RFC 1952), date from May 1996. *\[from the spec\]* With the format fixed, implementations compete on speed and parsing. zlib-ng's README says "x86-64 can be about 4x faster than stock zlib"; libdeflate runs levels to 12 for optimal parsing; Google's 2013 post on the compress-only Zopfli claims output "typically 3–8% smaller compared to zlib at maximum compression" for "2–3 orders of magnitude more" CPU time. *\[from the docs\]*

Brotli (RFC 7932, July 2016) adds context modelling and a built-in dictionary to LZ77 and Huffman coding. *\[from the spec\]* Its library and command line default to quality 11, the slowest; zstd's to level 3, zlib's to level 6. *\[from the docs\]* Default against default compares two efforts, not two formats. *\[reconstruction\]* The line that Brotli beats gzip by 20–26% swaps the baseline: Google's 2015 announcement said "20–26% higher compression ratios over Zopfli", and the Web Almanac 2025 repeats the figure against gzip, unsourced. *\[from the docs\]* On Silesia, brotli 11's output is 25.5% smaller than zlib -9's, and brotli 5's 12.7% smaller than zlib -6's. *\[measured here\]* For JSON, see [JSON: pick a level, then stop](2026-10-15-what-each-file-wants.md#03-json-pick-a-level-then-stop).

RFC 8478 (October 2018) registered Zstandard's media type and content coding; RFC 8878 (February 2021), which replaced it, is "not an Internet Standards Track specification". *\[from the spec\]* v1.5.7 (19 February 2025) is still the newest release. Levels run 1 to 19, default 3; `--ultra` unlocks 20 to 22 and `--fast` negative levels. *\[from the docs\]* `--long` and dictionaries are in [Saying it again, by reference](#04-saying-it-again-by-reference).

LZ4 and Snappy each describe themselves as an LZ77-type compressor with a fixed, byte-oriented encoding and no entropy coder; Apple's LZFSE adds FSE. *\[from the docs\]* xz and 7-Zip ship LZMA, which xz decodes with a range decoder: in XZ Utils 5.8.4, `src/liblzma/lzma/lzma_decoder.c` line 17 includes `range_decoder.h`. *\[from the docs\]* The 2024 xz backdoor is in [When compression is the attack](#09-when-compression-is-the-attack). Meta's OpenZL (6 October 2025) builds a graph of transforms from a description of the data, decodes everything with one decoder, and falls back to zstd. On `sao`, a Silesia star catalogue, Meta reports 2.06× against 1.31× for zstd -3 and 1.64× for xz -9, on an Apple M1; on text, "When there is no structure, there is no advantage." *\[from the docs\]* Figure 9 collects them.

## 06 · Compression is prediction

A model that predicts the next byte well leaves the coder little to pay for. The best lossless compressors are therefore the best predictors, and neural networks now win at the frontier. Headline numbers hide the model: its size, and the time to run it again at the other end.

Delétang et al. open "Language Modeling Is Compression" (ICLR 2024) with the equivalence: "It has long been established that predictive models can be transformed into lossless compressors and vice versa." *\[from the paper\]* With an arithmetic coder ([A model and a coder](#03-a-model-and-a-coder)), the output is the model's log loss summed over the file, plus a few bits. *\[reconstruction\]*

### The Hutter Prize

The Hutter Prize asks for a compressor of size S1 that turns enwik9, 10⁹ bytes of text, into a self-extracting archive of size S2. The score S = S1 + S2 must beat the record L, and pays €500,000 × (1 − S/L) for a gain of at least 1%, for a run of at most about 50 hours on one CPU core in under 10 GB of RAM (prize page, modified 30 September 2026). *\[from the docs\]*

The record moved three times in 2026 (Figure 11). It had stood at fx2-cmix's 110,793,128 bytes, dated 3 September 2024; cmix-lex (26 June) and cmix-obias (19 July) each cleared the 1% minimum. Then Vladimir Ivanov's fx2-cmix-T (24 July, awarded 30 September) reached 100,424,672, 7.46% below cmix-obias, and 7.46% of €500,000 is the €37,300 it won. *\[from the docs\]* The Large Text Compression Benchmark (LTCB), which calls it fx2-cmix-transformer, says it replaced fx2-cmix's LSTM "with a transformer with 6M parameters pre-trained on enwik9 on 8 RTX 5090 GPUs for 26 hours, adding 2.9 MB to the compressor and decompressor. It does not need a GPU to run." *\[from the docs\]* James Byrne's zmix write-up, quoted on LTCB: "The score counts the weights twice, once in the compressor and once in the archive". *\[from the docs\]*

### What this means for agents

A model's weights are a dictionary both ends already hold, like Brotli's built-in one or a trained zstd dictionary ([Saying it again, by reference](#04-saying-it-again-by-reference); measured in [Small messages and dictionaries](2026-10-15-what-each-file-wants.md#04-small-messages-and-dictionaries)), at 140 GB instead of kilobytes. A dictionary shared in advance is fairly left out of a ratio; one that must be shipped dominates it. *\[reconstruction\]* Both ends must also predict identically. Bellard's ts_zip, an RWKV 169M model driving an arithmetic coder, says "The model is evaluated in a deterministic and reproducible way." *\[from the docs\]*

For an agent, the cost that matters is the context both ends share: the weights, and what sits in the window. When the window fills, agents do not compress it losslessly. They compact it: a summary replaces older turns, and no decoder can recover what the summariser left out ([Compacting a conversation](#11-compacting-a-conversation)). *\[reconstruction\]*

## 07 · Throwing away what nobody sees

Lossless compression asks how few bits carry the data. Lossy compression asks how few carry it at a distortion that a model of the viewer or listener tolerates. The saving is a rounding no decoder can undo.

### A rate for a fidelity

Shannon posed the question in 1948 ([Information is surprise](#02-information-is-surprise)). Section 28 defines a source's rate "for a given quality v₁ of reproduction"; by Theorem 21, a channel of capacity C carries the source at fidelity as near v₁ as desired if that rate is at most C, and not if it is larger. *\[from the paper\]* His 1959 paper, "Coding Theorems for a Discrete Source With a Fidelity Criterion" (*IRE International Convention Record*, pp. 142–163), names the curve: "For coding purposes where a level d of distortion can be tolerated, the source acts like one with information rate R(d)." R(d) falls as d grows and is "convex downward". *\[from the paper\]* Each extra unit of distortion saves fewer bits than the one before. *\[reconstruction\]*

### Transform, quantise, code

In JPEG (ITU-T T.81, approved 18 September 1992, §4.3), the forward DCT turns each 8 × 8 block into 64 coefficients, each is quantised with "one of 64 corresponding values from a quantization table", and a Huffman or arithmetic coder codes the result ([A model and a coder](#03-a-model-and-a-coder)). *\[from the spec\]* The DCT is from Ahmed, Natarajan and Rao, "Discrete Cosine Transform" (*IEEE Transactions on Computers* C-23(1), January 1974), who found it close to the optimal Karhunen–Loève transform. *\[from the paper\]* It is invertible: it only concentrates a smooth block's energy, and the rounding does the forgetting. *\[reconstruction\]*

Figure 12 runs these steps in pure Python (`_compute.py` lines 1755–1812) on a synthetic ramp, 100 + 6x + 4y. *\[from the tree\]* Of nine nonzero coefficients, all in the first row or column, T.81's example luminance table keeps 5 and rounds the 4 highest-frequency ones to 0: 59 zeros in 64. No pixel decodes more than 3 levels off; squared errors sum to 156, mean 2.4375, so PSNR is 10 log₁₀(255² / 2.4375) = 44.26 dB. A second ramp, 90 + 4x + 3y with a step of 70 at mid-block, rings at the edge: up to 5 levels low on the dark side, 6 high on the bright side, 38.71 dB. *\[measured here\]*

Step 2, the forward DCT of ITU-T T.81: 64 coefficients, 9 of them nonzero to one decimal, all in row 0 or column 0: 56.0, −109.3, −11.4, −3.4 and −0.9 along the first row, −72.9, −7.6, −2.3 and −0.6 down the first column. Worked examples: 56.0 ÷ 16 = 3.5 rounds to 4, a tie rounded away from zero; −109.3 ÷ 11 ≈ −9.94 rounds to −10, decoded as −110; −3.4 ÷ 40 ≈ −0.085 rounds to 0 and is gone. Step 4, entropy coding: in zig-zag order the values are 4, −10, −6, 0, 0, 0, −1, 0, 0, −1, then 54 zeros at indices 10 to 63, passed to a Huffman or arithmetic coder. Step 5, decoding: multiply by the table, inverse DCT, add 128; the reconstructed block differs from the original by at most 3 levels, a PSNR of 44.26 dB. Green cells are nonzero after quantisation, red cells are nonzero coefficients rounded to zero, white cells are zero; thin blue arrows carry the data from step to step.](2026-10-15-what-compression-keeps/fig-12-transform.svg)

*\[measured here\]* `dct_demo.blocks` in `_numbers.json`: T.81's DCT (A.3.3), Table K.1 unscaled, rounding half away from zero; rows are vertical frequency, columns horizontal. *\[reconstruction\]* The block is synthetic, smoother than a photograph. The loss happens at step 3: the decoder gets back rounded multiples of the table, not the coefficients.

### Where perception enters

It enters at the table. T.81's Annex K tables "are based on psychovisual thresholding" and "are provided as examples only"; the standard sets no default (§4.3, §K.1). *\[from the spec\]* In audio, Opus's CELT layer yields "coding noise that has the same spectral envelope as the signal", an envelope that a standard psychoacoustic model's masking curve also closely follows (RFC 6716 §4.3.3). Opus defaults to VBR; its constrained VBR, which simulates a "bit reservoir", is what MP3 and AAC call CBR (§2.1.8). *\[from the spec\]* The AV1 specification defines the bitstream and the decoding process; encoding is "A process not specified in this Specification". *\[from the spec\]* Two encoders of one format can differ widely at equal size. *\[reconstruction\]*

### Measuring what was lost

Netflix's "Toward A Practical Perceptual Video Quality Metric" (6 June 2016) says PSNR "does not consistently reflect human perception", yet "remains the de facto standard for codec comparisons". At about 31 dB each, viewers gave a crowd clip a DMOS of 82 and a fox clip 27, on a scale where 100 means the impairments are imperceptible. *\[from the docs\]* SSIM (Wang, Bovik, Sheikh and Simoncelli, "Image quality assessment: from error visibility to structural similarity", *IEEE Transactions on Image Processing* 13(4), April 2004) scores lost structure. *\[from the paper\]* VMAF, Netflix's learned fusion of elementary metrics, got v1 models in June 2026; FFmpeg's `libvmaf` filter still defaults to `vmaf_v0.6.1`. SSIMULACRA 2 (Cloudinary, 2022) puts "visually lossless" at 90; XPSNR (Helmrich et al., ICASSP 2020) weights PSNR perceptually. *\[from the docs\]* Codecs are compared by BD-rate, the average percentage difference in rate over a range of qualities, from at least four points per codec (draft-ietf-netvc-testing-09 §4.2, an expired Internet-Draft). *\[from the spec\]*

Loss compounds. JPEG XL recompresses existing JPEGs losslessly, about 20% smaller by its authors' account, so that no "generation loss (additional compression artifacts caused by lossy transcoding)" enters the migration (Sneyers et al., "The JPEG XL Image Coding System: History, Features, Coding Tools, Design Rationale, and Future", arXiv:2506.05987, 2025). *\[from the paper\]* Keep the lossless master. *\[reconstruction\]* What Each File Wants measures the choices for [images](2026-10-15-what-each-file-wants.md#09-images), [audio](2026-10-15-what-each-file-wants.md#10-audio) and [video](2026-10-15-what-each-file-wants.md#11-video).

## 08 · Compression on the wire

In HTTP the browser lists the codings it can decode; the server picks one and names it. *\[from the spec\]* One 367,737-byte page from this site travels as 68,906 bytes of Brotli 11, and as 61,970 with a sibling post as a shared dictionary. With its previous version as the dictionary, an 822,400-byte page that had grown by 808 bytes travels as 198. *\[measured here\]*

### Who chooses

On the web, compression belongs to the content. RFC 9110 §8.4 calls the codings in Content-Encoding "a characteristic of the representation"; RFC 9112 §6.1 says "Transfer-Encoding is a property of the message, not of the representation." *\[from the spec\]* HTTP/2 forbids Transfer-Encoding (RFC 9113 §8.2.2), so web compression is Content-Encoding, negotiated by Accept-Encoding with optional q-values (RFC 9110 §12.5.3). *\[from the spec\]*

Chromium offers `br` and `zstd` only over HTTPS or to localhost; a comment in `net/http/http_request_headers.cc` says to advertise br "only if transferred data is opaque to proxy". *\[from the docs\]* `dcb` and `dcz` are RFC 9842's dictionary-compressed Brotli and zstd codings (§4, §5; A dictionary sent once, below). *\[from the spec\]* The table gives first versions from MDN and caniuse, and what two CDNs do. *\[from the docs\]* Green marks a coding on by default or served, orange one that is partial, flagged or in beta, red one absent or undocumented.

### A dictionary sent once

Compression Dictionary Transport, RFC 9842 (September 2025, Standards Track), lets one response serve as the dictionary for later ones. *\[from the spec\]* The response opts in with `Use-As-Dictionary`, whose `match` pattern names the URLs it covers. A later matching request sends `Available-Dictionary`, the SHA-256 of the stored bytes, and `Dictionary-ID` if the server set an id. The server may answer `dcb`, a 36-byte header (`ff 44 43 42` and the hash) before a Shared Brotli stream (RFC 9841) with at most a 16 MB window, or `dcz`, a 40-byte zstd skippable frame holding the hash before a zstd frame. *\[from the spec\]* Clients must not offer dcb or dcz without a matching dictionary, and cacheable responses must vary on `accept-encoding, available-dictionary`. *\[from the spec\]* zstd, unlike Brotli, reaches the dictionary only within its window, so dcz decoders must accept a window of 8 MB or 1.25 times the dictionary, whichever is greater, up to 128 MB. *\[from the spec\]* Matching is same-origin only (RFC 9842 §9.3.1; [When compression is the attack](#09-when-compression-is-the-attack)). *\[from the spec\]*

## 09 · When compression is the attack

Compression makes output length depend on content, so a length can leak a secret. It lets a few hundred bytes stand for a gigabyte, so a small file can exhaust a machine. And in 2024 a compression library's release tarballs carried a backdoor.

### A length that leaks

CRIME (CVE-2012-4929; Duong and Rizzo, ekoparty, September 2012) recovered cookies from TLS-level compression by injecting chosen plaintext and measuring the encrypted size. *\[from the docs\]* BREACH (CVE-2013-3587; Black Hat USA 2013) did the same to HTTP bodies: any compressed page that reflects user input beside a secret is exposed, for "just a few thousand requests". *\[from the docs\]*

HEIST (Vanhoef and Van Goethem, Black Hat USA 2016) moves the attacker into the browser: a script times whether a response fits in TCP's initial congestion window to learn "the exact size of any cross-origin response". *\[from the paper\]* TLS 1.3 offers only the null compression method (RFC 8446 §4.1.2), *\[from the spec\]* which ends CRIME but not the other two. *\[reconstruction\]*

Figure 15 rebuilds BREACH on a synthetic 2,008-byte inbox page. The secret, 32 hex characters, sits in a sign-out link; the search line reflects `csrf_token=` plus a guess whose first k characters are right. From k = 0 to 32, raw DEFLATE-6 shrinks from 737 to 711 bytes; brotli 5 and zstd 3 save 26 and 23. *\[measured here\]* Guessed character by character, the right candidate is never beaten under DEFLATE but is tied at 19 of 32 positions, *\[measured here\]* so an attacker needs more than one length per guess; *\[reconstruction\]* under brotli and zstd a wrong one wins at 4 and 5 positions. *\[measured here\]*

### A backdoor in the release tarball

On 29 March 2024 Andres Freund reported on oss-security that "The upstream xz repository and the xz tarballs have been backdoored". ## 10 · Compaction: keeping only the present

A system that writes out of place leaves old versions behind. Compaction rewrites what is still live and lets the rest go. Each kind keeps an invariant, drops what no reader can see, waits for a trigger, and pays in writes, spare disk or a pause.

### What each one promises to keep

The sources state the invariant themselves. SQLite's `VACUUM INTO` output "will contain the same logical content as the original database, fully vacuumed" (lang_vacuum.html, §2.1). Delta Lake: "a read before and after an OPTIMIZE has the same results" (Delta 4.4.1). Kafka: "The offset for a message never changes" (4.3 docs, Design). Cassandra keeps "the most up-to-date version (by timestamp)" of each column ("Compaction overview"). *\[from the docs\]*

The promises cover logical content, not physical identity. SQLite's VACUUM "may change the ROWIDs" of tables without an explicit INTEGER PRIMARY KEY (§3). *\[from the docs\]* In one test here on 3.46.1 it changed none of 2,000. *\[measured here\]* A copying collector moves every survivor; in V8's scavenger each copied object "leaves a forwarding-address" ("Trash talk", 3 January 2019). *\[from the docs\]*

### LSM trees

A log-structured merge tree buffers writes in memory and merges them down through ever larger sorted files (Figure 17). O'Neil et al. (*Acta Informatica*, 1996) called this the "rolling merge"; their preprint never says compaction. Its "delete node entry" migrates down and "annihilates the associated entry when it is encountered" (§2.3), the ancestor of the tombstone. *\[from the paper\]* Bigtable (OSDI 2006, §5.4) named the steps: a minor compaction flushes the memtable (the sorted in-memory buffer) to an SSTable (a sorted, immutable file), a merging compaction bounds how many SSTables a read must merge, and a major compaction "produces an SSTable that contains no deletion information or deleted data". *\[from the paper\]*

RocksDB defines the costs. Write amplification is "the ratio of bytes written to storage versus bytes written to the database"; space amplification is bytes on disk over data size. Leveled compaction keeps space low and rewrites more; universal compaction writes less but "may temporarily increase size amplification by a factor of two" (Tuning Guide). *\[from the docs\]* The RUM conjecture generalises: "An access method that can set an upper bound for two out of the read, update, and memory overheads, also sets a lower bound for the third overhead" (Athanassoulis et al., EDBT 2016, §3). *\[from the paper\]*

RocksDB compresses as it compacts. Since 11.5.0 (16 June 2026) the default block codec is LZ4 where compiled in; v11.8.1, the latest tagged release, ships it. The wiki recommends ZSTD for the bottommost level, which "contains majority of the data". With dictionary compression on, a dictionary is trained per SST file during compaction. *\[from the docs\]* The codecs themselves are in [The codecs that matter in 2026](#05-the-codecs-that-matter-in-2026).

Cassandra 5.0's docs recommend the Unified Compaction Strategy "for most workloads" over the size-tiered, leveled and time-window strategies. 5.0.9 (7 August 2026) is the latest GA release; 6.0 exists only as alphas. A tombstone may be purged only after `gc_grace_seconds` (default 864000, ten days), by a compaction that includes every SSTable with older data for its partition. Purge sooner, and a replica that missed the delete can spread the row back as a "zombie". *\[from the docs\]*

### Kafka: at least the last value

A topic with `cleanup.policy=compact` keeps "at least the last known value for each message key" in a partition (4.3 docs, "Log Compaction"). At least, not only. The cleaner recopies closed segments, never the active one, once the dirty share reaches `min.cleanable.dirty.ratio` (default 0.5): "at most 50% of the log could be duplicates". A tombstone, a key with a null payload, is itself removed after `delete.retention.ms` (default one day), so a consumer lagging longer can miss the delete. Batch compression is a separate setting ([why batches compress](2026-10-15-what-each-file-wants.md#04-small-messages-and-dictionaries)). *\[from the docs\]* Figure 18 shows one cleaning.

### Databases: deleting is not freeing

PostgreSQL keeps old row versions for multiversion concurrency control (MVCC) ([Where the JSON Lives](2026-10-15-where-the-json-lives.md#02-the-relational-family)). Plain `VACUUM` marks their space reusable without blocking reads or writes. `VACUUM FULL` "actively compacts tables by writing a complete new version of the table file with no dead space", under an ACCESS EXCLUSIVE lock, and autovacuum "will never issue VACUUM FULL" (PostgreSQL 18 docs, §24.1.2 and "VACUUM"). PostgreSQL 19's `REPACK`, in beta, takes that lock only to swap files when run with `CONCURRENTLY`. *\[from the docs\]*

SQLite's VACUUM "rebuilds the database file, repacking it into a minimal amount of disk space", and may need twice the file size free. With `auto_vacuum` off, the default, freed pages go on a freelist; `auto_vacuum=FULL` truncates it at each commit but "can actually make fragmentation worse". *\[from the docs\]* In Figure 19, deleting 90% of 100,000 generated JSON documents leaves the 47,034,368-byte file exactly that size, with 10,332 of its 11,483 pages free. VACUUM brings it to 4,714,496 bytes and writes 14,154,268 to get there, three times what it leaves (14,154,268 ÷ 4,714,496 = 3.00). After a scattered delete, `incremental_vacuum` ended 12% larger than VACUUM (5,300,224 against 4,722,688 bytes) and left 78 deleted documents readable in unused gaps of live pages; VACUUM left none. *\[measured here\]* This build compiles in `SECURE_DELETE`, so the remnant count does not generalise. *\[reconstruction\]*

MongoDB's `compact` "Attempts to release unneeded disk space to the operating system", and 8.0 added a background `autoCompact`. etcd splits the job: compaction drops superseded key versions, and a separate defragmentation, which blocks the member, returns the space (v3.7 docs, "Maintenance"). *\[from the docs\]*

Iceberg's `rewrite_data_files` bin-packs small files towards 512 MB, and each compaction is a new snapshot: old files stay for time travel until `expire_snapshots` (Iceberg 1.12.0 docs). Its default Parquet codec is zstd. *\[from the docs\]* Because these rewrites, and Delta's `OPTIMIZE`, write new files, compaction is when a changed codec reaches old data. *\[reconstruction\]*

### Memory, disks, git and logs of record

V8's mark–sweep–compact collector compacts only some highly fragmented pages: "You can think of compaction sort of like hard-disk defragmentation on an old PC." G1 compacts as it evacuates live objects (Java 26 tuning guide); ZGC relocates concurrently and has been generational only since JDK 24 (JEP 490). Linux compacts physical memory for huge pages, in per-node `kcompactd` threads since 4.6, and its docs warn of latency spikes. *\[from the docs\]* These move live data and drop nothing live. *\[reconstruction\]*

The log-structured file system (Rosenblum and Ousterhout, SOSP 1991, §3.4) prices cleaning as write cost: disk time per byte of new data. *\[from the paper\]* Reading N segments at utilisation u, writing back N·u of live data and filling N·(1 − u) with new data moves 2N segments for N·(1 − u) of new data: 2 ÷ (1 − u), or 10 at 80% live. *\[reconstruction\]* F2FS cleans the same way on flash. *\[from the docs\]*

`git gc` does both jobs (its manual is quoted in [the opening section](#01-fewer-bits-or-fewer-things)); a pack holds objects "individually compressed, with delta compression applied" (git-repack.adoc). *\[from the docs\]* On a synthetic 300-commit repository (24 files; a deleted five-commit branch adds five 256 KiB files), git 2.55.0's `git gc --prune=now` packed 1,646 of 1,661 loose objects, 1,010 as deltas, dropped the 15 unreachable ones, and cut `.git/objects` from 7,561,216 bytes on disk to 253,952 (1,931,211 to 241,355 apparent bytes). *\[measured here\]* Each loose object occupies whole 4 KiB filesystem blocks, so on-disk bytes overstate the drop. *\[reconstruction\]* By default, unreachable objects get two weeks' grace (`gc.pruneExpire`). *\[from the docs\]*

Raft compacts by snapshot: "the entire current system state is written to a snapshot on stable storage, then the entire log up to that point is discarded" (extended version, 2014, §7). *\[from the paper\]* Event sourcing as Martin Fowler defines it (2005) keeps the events "for the same lifetime as the application state itself"; its snapshots are a cache. *\[from the docs\]* Yjs, a CRDT, discards a deleted item's content but keeps the item as a tombstone, because it fixes the order; `doc.gc = false` keeps the content too. *\[from the docs\]* An agent's context is the newest sense: [Compacting a conversation](#11-compacting-a-conversation).

## 11 · Compacting a conversation

When an agent's context window fills, the agent replaces older turns with a summary that a model writes: lossy compression of meaning, plus eviction. Storage compactions keep an exact logical state. This one keeps what the summariser judged relevant.

### What the vendors document

Claude Code's `/compact` will "Free up context by summarizing the conversation so far", and it compacts unprompted: "It clears older tool outputs first, then summarizes the conversation if needed. Your requests and key code snippets are preserved; detailed instructions from early in the conversation may be lost." *\[from the docs\]* Models with a native 1M-token window compact "at about 967K tokens by default". *\[from the docs\]* Anthropic's engineering post "Effective context engineering for AI agents" (29 September 2025) describes passing the history to the model "to summarize and compress the most critical details." *\[from the docs\]* Docs read 9 October 2026, when Claude Code 2.1.295 was the latest npm release. *\[from the docs\]*

The Claude API writes the summary on the server. *\[from the docs\]* Threshold compaction (beta header `compact-2026-01-12`, strategy `compact_20260112`) triggers at 150,000 input tokens by default, never below 50,000. ### The one compaction without an invariant

Storage compactions state their invariant: the same logical content, or at least the final state of every key ([Compaction: keeping only the present](#10-compaction-keeping-only-the-present)). *\[from the docs\]* Context compaction has none. The same Anthropic post: "The art of compaction lies in the selection of what to keep versus what to discard, as overly aggressive compaction can result in the loss of subtle but critical context whose importance only becomes apparent later." *\[from the docs\]* Unlike lossy media coding ([Throwing away what nobody sees](#07-throwing-away-what-nobody-sees)), it has no distortion metric: no published measure of what these summaries lose was found, and none is measured here. *\[reconstruction\]*

It is the one compaction that needs a human-readable audit trail. A database forgets versions nobody will ask for; an agent's early turns may be wanted later, by a person checking its work. Keep the transcript ([stored like any log](2026-10-15-what-each-file-wants.md#07-logs-and-json-lines)), record each boundary with its token counts, log each summary, and put durable facts in files, because files come back exactly. *\[reconstruction\]* Claude Code's `PostCompact` hook exists "to react to the new compacted state, for example to log the generated summary or update external state". *\[from the docs\]* An opaque item can be stored but not audited. In xo-space, the empty fields are where that trail would start. *\[reconstruction\]*

## 12 · Compression and compaction, side by side

Compression changes how the data is written. Compaction changes which data there is. Lossless compression can be undone; compaction usually cannot. They meet inside storage engines, where their order matters.

### Two definitions

**Compression** changes the encoding: the same data in fewer bits, judged by ratio, by speed and, if lossy, by distortion. Lossless compression is reversible. **Compaction** rewrites the live data densely and drops what no reader can observe any more. It is judged by write, read and space amplification and by pauses, and it cannot be undone. *\[reconstruction\]*

The sources force two refinements. Some compactions drop nothing. Linux memory compaction moves pages "such that free memory is available in contiguous blocks where possible" (`Documentation/admin-guide/sysctl/vm.rst`, `compact_memory`), and e4defrag(8) and Windows `defrag` only consolidate files. *\[from the docs\]* So the defining act is reorganising for the present, and discarding is the common case. LLM context compaction is a third kind: lossy, semantic and irreversible ([Compacting a conversation](#11-compacting-a-conversation)). *\[reconstruction\]* Figure 21 sets every kind side by side; Figure 22 asks two questions of it.

### Where they meet

Several systems compress while they compact. RocksDB skips compaction "trivial moves" that would break per-level codecs and rewrites the file instead (wiki, "Compression"). Cassandra warns that after `ALTER TABLE` "the compression will not be modified until the table is compacted" ("Compression"). In git, a changed level "will not automatically recompress all existing objects" without `git repack -F` (`config/pack.adoc`). *\[from the docs\]* Iceberg and Delta rewrites write new files with the table's current codec. *\[reconstruction\]*

Other systems keep them apart. Kafka has `cleanup.policy=compact` for which records stay and `compression.type` (default `producer`) for how batches are encoded (4.3 docs). MongoDB's `compact` releases obsolete blocks; WiredTiger compresses most collections with snappy by default. *\[from the docs\]* Bigtable (OSDI 2006) treats compactions in §5.4 and compression in §6. *\[from the paper\]* Order matters: compact first, then compress (Figure 2). *\[reconstruction\]*

### Five things often said

- **Compaction is a kind of compression.** Not now: even engines that do both in one pass expose them as separate settings (RocksDB's per-level codec, Cassandra's table compression options). In the 1970s the words overlapped ([Fewer bits, or fewer things](#01-fewer-bits-or-fewer-things)). *\[reconstruction\]*
- **Kafka compaction keeps only the latest value.** It keeps at least the latest value per key and never cleans the active segment ([Compaction](#10-compaction-keeping-only-the-present), Figure 18). *\[from the docs\]*
- **Deleting data frees disk space.** etcd: "deleting application data does not reclaim the space on disk" (v3.7, "Maintenance"). *\[from the docs\]* SQLite with `auto_vacuum` off behaves the same (Figure 19). *\[measured here\]*
- **Compaction always shrinks storage.** It often grows it first, and between cleanings a log never holds just the live state (universal compaction and the cleaner model in [Compaction](#10-compaction-keeping-only-the-present), Figure 19). *\[reconstruction\]*
- **VACUUM FULL is the normal fix for bloat.** PostgreSQL: "The usual goal of routine vacuuming is to do standard VACUUMs often enough to avoid needing VACUUM FULL" (18 docs, §24.1.2). *\[from the docs\]*

### Compact JSON sits between

jq calls its `-c` flag `--compact-output` (jq 1.8 manual). *\[from the docs\]* Minifying removes bytes like compression, because "Insignificant whitespace is allowed before or after any of the six structural characters" (RFC 8259 §2). *\[from the spec\]* It loses no data, only formatting, and that loss is one-way, like compaction: the value survives, the layout does not. *\[reconstruction\]* Compression makes most of it moot; What Each File Wants measures how little of the saving survives a codec on three corpora ([its minify figure](2026-10-15-what-each-file-wants.md#03-json-pick-a-level-then-stop)): after brotli 11, 2.88% to 5.34%. *\[measured here\]*

### A decision rule

Ask whether anyone needs the past. If so, compress, and copy the history out before any compaction. If not, compact. Then ask whether every byte must survive: if so, compress losslessly; if a perceptual model may choose, go lossy. When both apply, compact first and compress what is left. An agent's context has no exact answer, so keep the transcript beside the summary. *\[reconstruction\]*
