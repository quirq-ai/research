## 1. What qq is

qq (quirq infra) is quirq's build, test and land system. It is modelled on
Chromium's infrastructure and rebuilt for small GitHub repos.

- **One config repo decides everything.** infra-config declares every repo,
  builder, gate rule and channel as TOML. The tools that apply policy read it
  at a pinned commit.
- **A product repo writes one file by hand,** its manifest `infra/repo.toml`.
  Everything else (CI workflows, rulesets, rolls) is generated or delivered by
  PR.
- **`qq` is the command line.** It builds and tests a repo the same way on
  every machine, from what the manifest says. You never need to know the
  repo's language or package manager.
- **Who uses it.** Two product repos: xo-space (Python) and innernet
  (Next.js). website (Gatsby) is being onboarded.

Source: [v0 status report](2026-10-05-qq-v0-status.md), "In one minute".

## 2. The 13 repos

The repos fall into four stages by where they act on a change. The grouping is
this topic's; each repo's job is from its README.

| Stage | Repo | Its job | Chromium counterpart |
|---|---|---|---|
| Your machine | depot | the `qq` command line | depot_tools |
| Your machine | sync | the manifest schema and its only parser, `qqsync` | gclient, DEPS |
| Your machine | recipes | one adapter per target kind | recipes |
| Your machine | toolchains | Python and Node, built, promoted and pinned by digest | CIPD, 3pp |
| Your machine | remote-build | where actions run, and their cache | goma, reclient, RBE |
| Before landing | infra-config | all policy and builder definitions as data | infra/config, lucicfg |
| Before landing | gate | the required checks and the merge queue | LUCI CV |
| Before landing | test-pipelines | stored results, verdicts, failure records | ResultDB, LUCI Analysis |
| After landing | gardener | keeps `main` green: tree status, bisection, reverts | Sheriff-o-Matic, LUCI Bisection |
| After landing | rollers | keeps dependencies and toolchains current | AutoRoll |
| After landing | perf | performance numbers per commit | chrome.perf, Pinpoint |
| Shipping | release | `lkgr`, channels, the daily canary, rollback | lkgr finder, promote.py |
| Shipping | installer | clients follow a channel instead of `main` | chrome/updater |

How they connect: policy flows down from infra-config, results flow back up
through test-pipelines, and every link between repos is a pinned commit, never
copied code. The [infra map](../app/infra-map/) draws every link with its
source.

Source: [phases report](2026-10-05-qq-phases.md), "How qq is laid out";
[v0 status report](2026-10-05-qq-v0-status.md), "How the repos fit together".

## 3. How a change travels

A developer, human or agent, writes code as usual and lets qq decide whether
it lands. Notes in italics say what is true today.

1. **Set up once.** Install `qq` and `qqsync` (section 4).
2. **Get toolchains.** `qq sync` fetches each pinned toolchain, checks its
   digest and links it under `.qq/toolchains/`. *Linux x86_64 only; on a Mac
   you bring your own.*
3. **Build and test.** `qq build` and `qq test` run the same steps CI runs and
   leave results in `.qq/out`.
4. **Open a PR.** The generated `<repo>-presubmit` check runs: a drift check,
   then fetch, build and test, then every JUnit result is stored in
   test-pipelines.
5. **Ask for a verdict.** `qq try` returns a run ID at once and reports the
   verdict later; `qq status` gives it on demand (exit 0 pass, 1 refused,
   3 pending).
6. **Land.** `qq land` asks the gate for a verdict, then queues the PR. The
   merge queue re-runs the check on the exact merge result and squash-merges.
7. **After it lands.** The post-submit builder runs on every `main` commit.
   gardener publishes tree status every 5 minutes; if `main` goes red it finds
   the culprit and proposes a revert. *Reverts need the gardener GitHub App,
   which does not exist yet.*
8. **Dependencies move.** Dependabot opens update PRs and `qq-roll-land`
   checks them. *Auto-land is off, so a person merges every roll.*
9. **Ship.** release moves `lkgr` to the newest all-green `main` commit, and
   the daily canary builds, tests, deploys and probes it before moving the
   canary channel. *The first canary shipped both repos on 2026-10-05, started
   by hand.*
10. **Install from a channel.** `qqinstall resolve --repo xo-space --channel
    canary` gives the commit and digest to install.
11. **Measure.** perf records build size and a benchmark per `main` commit,
    as a record only, never a gate.

Source: [v0 status report](2026-10-05-qq-v0-status.md), "How a developer uses
it".

## 4. Use qq on your machine

### Before you start

- **git**, and **python3 3.11.4 or newer** with its `venv` module.
- **Network** to github.com, PyPI and ghcr.io. No login is needed.
- **Linux x86_64** gets every toolchain fetched for it. **On a Mac**, `qq sync`
  stops with "no pin for platform …", so you install the pinned versions
  yourself: CPython **3.14.8** from python.org for xo-space, Node **24** and
  pnpm for innernet.

Every command below runs inside `( … )`, so your folder and environment never
change, and each one is safe to run again. Your files live in `~/qq-tools`
(the tools) and `~/qq-try` (practice copies), both safe to delete.

### Install (run again any time to update)

**depot (`qq`).** Ends with `qq 0.1.0`.

```sh
( set -e; mkdir -p ~/qq-tools; rm -rf ~/qq-tools/depot; git clone -q https://github.com/quirq-ai/depot ~/qq-tools/depot; ~/qq-tools/depot/bin/qq --version )
```

**sync (`qqsync`).** Ends with `qqsync 0.1.0`.

```sh
( set -e; mkdir -p ~/qq-tools; rm -rf ~/qq-tools/qqsync; python3 -m venv ~/qq-tools/qqsync; ~/qq-tools/qqsync/bin/pip install -q --disable-pip-version-check "qqsync @ git+https://github.com/quirq-ai/sync@main"; ~/qq-tools/qqsync/bin/qqsync --version )
```

**Optional: type `qq` and `qqsync` without the full path.** This adds
`~/qq-tools/bin` to `PATH` in `~/.zshrc` once; open a new terminal afterwards.

```sh
( mkdir -p ~/qq-tools/bin && ln -sf ~/qq-tools/depot/bin/qq ~/qq-tools/qqsync/bin/qqsync ~/qq-tools/bin/ && { grep -qs 'qq-tools/bin:' ~/.zshrc || printf '\nexport PATH="$HOME/qq-tools/bin:$PATH"\n' >> ~/.zshrc; } )
```

### The loop, for any repo with a manifest

| Step | Command | What it does |
|---|---|---|
| 1. Get the code | `qq fetch https://github.com/quirq-ai/NAME` (Linux), or `git clone` (Mac) | clones; on Linux it also syncs |
| 2. Sync | `qq sync` | fetches pinned toolchains, checks digests |
| 3. See the targets | `qqsync show infra/repo.toml` | prints the manifest and its targets |
| 4. Build | `qq build [TARGET]` | installs dependencies and builds |
| 5. Test | `qq test [TARGET]` | builds, then tests; results in `.qq/out/results.json` |
| 6. Run | the repo's own start command | there is no `qq run` yet |

On a Mac, add `--toolchain python=ROOT` to `qq build` and `qq test` for a
pinned Python, where `ROOT/bin/python3` is exactly the pinned version. A Node
app uses the `node` and `pnpm` on your `PATH`.

### Example: xo-space (Python)

Get the code. On Linux:

```sh
( set -e; mkdir -p ~/qq-try; cd ~/qq-try; rm -rf xo-space; ~/qq-tools/depot/bin/qq fetch https://github.com/quirq-ai/xo-space; ls xo-space/.qq/toolchains )
```

On a Mac:

```sh
( set -e; mkdir -p ~/qq-try; cd ~/qq-try; rm -rf xo-space; git clone -q https://github.com/quirq-ai/xo-space )
```

Build the server (on a Mac, add
`--toolchain python=/Library/Frameworks/Python.framework/Versions/3.14`):

```sh
( cd ~/qq-try/xo-space || exit 1; ~/qq-tools/depot/bin/qq build server )
```

Test (the same flag on a Mac):

```sh
( cd ~/qq-try/xo-space || exit 1; QUIRQ_STATE_ROOT=$HOME/qq-try/state RCLONE_CONFIG=$HOME/qq-try/state/rclone.conf ~/qq-tools/depot/bin/qq test route-parity; echo "qq test finished with exit $? (0 means every check passed)" )
```

Run it, then open **http://127.0.0.1:5002/space/**; **Ctrl-C** stops it. The
settings keep everything it writes inside `~/qq-try/xo-space-home`.

```sh
( P=~/qq-try/xo-space-home; mkdir -p $P/workspace; cd ~/qq-try/xo-space || exit 1; HOME=$P STAGE=local QUIRQ_SKIP_BOOT_INSTALL=1 AGENT_NAME=claude_code XO_PROJECTS_ROOT=$P/workspace AI_WORKSPACE_ROOT=$P/workspace QUIRQ_STATE_ROOT=$P/.quirq PORT=5002 .qq/venv/bin/python server.py )
```

### Example: innernet (Next.js)

Get the code. On Linux:

```sh
( set -e; mkdir -p ~/qq-try; cd ~/qq-try; rm -rf innernet; ~/qq-tools/depot/bin/qq fetch https://github.com/quirq-ai/innernet; ls innernet/.qq/toolchains )
```

On a Mac:

```sh
( set -e; mkdir -p ~/qq-try; cd ~/qq-try; rm -rf innernet; git clone -q https://github.com/quirq-ai/innernet )
```

Build and test in one step, as the public demo:

```sh
( cd ~/qq-try/innernet || exit 1; INNERNET_DEMO=1 ~/qq-tools/depot/bin/qq test; echo "qq test finished with exit $? (0 means every check passed)" )
```

Run it, then open **http://127.0.0.1:3470**; **Ctrl-C** stops it.

```sh
( cd ~/qq-try/innernet || exit 1; PATH="$PWD/.qq/toolchains/node/bin:$PATH" pnpm start )
```

### Cheat sheet

| Command | What it does | Exit |
|---|---|---|
| `qq fetch <url> [dir]` | clone, then `qq sync` in it | 0 ok, 1 failed |
| `qq sync` | fetch every pin, check its digest, link it under `.qq/` | 0 ok, 1 fetch or pin failed, 2 no or bad manifest |
| `qq build [TARGET …]` | build targets as CI does | 0 passed, 1 a step failed, 2 no or bad manifest |
| `qq test [TARGET …]` | build and test; results in `.qq/out` | 0 passed, 1 a step failed, 2 no or bad manifest |
| `qqsync validate [FILE]` | check a manifest against `quirq-repo/1` | 0 PASS, 1 problems listed |
| `qqsync show [FILE]` | the manifest as JSON | 0 ok, 1 unreadable or invalid |
| `qqsync pins [FILE]` | list every pin and digest | 0 ok, 1 unreadable or invalid |
| `qqsync pin SECTION NAME --digest …` | set one pin, leaving other lines as they were | 0 ok, 1 bad manifest or pin |
| `qqsync guard [DIR]` | fail if anything else parses the manifest | 0 PASS, 1 findings |

After `qq test`, read `.qq/out/results.json`: it is rewritten on each run.
Every `FAIL` line names its log file.

### If something goes wrong

| You see | Do this |
|---|---|
| `no pin for platform macos-arm64` | You're on a Mac: `git clone`, then `--toolchain` for Python or your own Node 24 |
| `FAIL … toolchain-check`, log says `pinned CPython 3.14.8, found …` | Install CPython 3.14.8 and pass `--toolchain python=ROOT` |
| `FAIL … toolchain-check`, log says `pinned Node 24, found 22` | Install Node 24, or run on Linux after `qq sync` |
| `.qq/venv/bin/python: No such file or directory` | Build before you run (`qq build server`) |
| `Could not find a production build in the '.next' directory` | Run `qq test` before `pnpm start` |
| `qq: no infra/repo.toml here or above …` | The repo has no manifest: build it by hand, or add one (section 5) |
| `… already exists; run qq sync inside it instead` | Re-run the step as written; it deletes the old copy first |
| a fetch fails behind a proxy | Set `HTTPS_PROXY`; for your own CA set `SSL_CERT_FILE` and git's `http.sslCAInfo` |

### Remove everything

```sh
( chmod -R u+w ~/.cache/qq 2>/dev/null; rm -rf ~/qq-tools ~/qq-try ~/.cache/qq )
```

Delete the PATH line from `~/.zshrc` if you added it.

Source: [setup guide](2026-10-05-qq-setup-depot-sync.md) and
[build and run guide](2026-10-05-qq-build-run-locally.md), which have more
detail, a demo repo and every error case.

## 5. Add a repo to qq

### Give it a manifest

A repo needs one file, `infra/repo.toml`. This one has a single `pytest`
target:

```toml
schema = "quirq-repo/1"

[qq]
version = "0.1.0"

[[targets]]
name = "tests"
kind = "pytest"
srcs = ["tests/**", "requirements-dev.txt"]
```

Check it with `qqsync validate infra/repo.toml`, then `qq test`. Pick the kind
that fits:

| The repo is | Kind | It needs |
|---|---|---|
| a Python server or app | `python-service` | `requirements.txt`; the script to start (`params.entry`, or the first `.py` in `srcs`) |
| Python tests | `pytest` | `requirements-dev.txt` (including pytest) |
| a Next.js app | `node-app` | `package.json` with a `build` script and a `typecheck` or `test` script, and `pnpm-lock.yaml` |

Anything else (Go, Rust, a plain npm project) has no kind yet. Change pins only
with `qqsync pin`, and never parse the manifest yourself.

### Put it under qq's landing policy

Onboarding a repo in a language qq already knows takes PRs in three repos plus a
settings run, with no code change in any tool repo. The repo must be public in
quirq-ai.

| Order | Where | Change |
|---|---|---|
| 1 | the new repo | a PR with `infra/repo.toml` |
| 2 | infra-config `config/repos.toml` and `config/pipelines.toml` | a `[[repo]]` block, plus a blocking presubmit and a post-submit builder |
| 3 | the new repo | add the workflows from `qqcfg deliver` and rollers' Dependabot files to its PR, then merge it |
| 4 | gate `settings/github.toml` | a `[[repo]]` entry |
| 5 | suraj's terminal | the apply command below, once the repo's PR is on `main` and the gate PR has merged |
| 6 | GitHub | add the repo to the rollers App installation; turn on Dependabot |

The order matters: infra-config must list the repo before gate can name it,
and the required check must exist on the repo's `main` before the apply will
touch it. An apply run too early leaves the repo with no rulesets.

The apply, run by an org owner with `gh` logged in (replace `<COMMIT>` with
the gate commit you are given):

```sh
( mkdir -p ~/qq-apply && cd ~/qq-apply && rm -rf qq-gate && git clone -q https://github.com/quirq-ai/gate qq-gate && cd ./qq-gate && git checkout -q <COMMIT> && scripts/apply.sh )
```

It shows a dry run, writes only what is approved at its prompts, and is safe
to re-run.

Source: [operator guide](2026-10-05-qq-onboard-website.md), which walks
through every step with screenshots using quirq-ai/website;
[v0 status report](2026-10-05-qq-v0-status.md), "Adding a new repo".

## 6. Policy and owners

Every policy is a TOML file in infra-config's `config/`, changed by a pull
request. Repo settings are code in gate, applied with the one command above.

| Policy | File | Today's value |
|---|---|---|
| Who may land what | `gate.toml` | declared per change class; advisory today |
| Builders per repo | `pipelines.toml` | a blocking presubmit and a post-submit per repo |
| Toolchains and kinds | `kinds.toml` | Python 3.14, Node 24 (pnpm) |
| Auto-revert caps | `auto_revert.toml` | 10 per rolling 24 hours; none land on their own |
| Rolls | `rollers.toml` | Dependabot for pip and npm; weekly toolchain rotation |
| Channels | `channels.toml`, `health.toml` | canary automatic and daily; dev needs a human owner; stable needs the policy-owner |
| Repo rulesets and merge queue | gate `settings/github.toml` | applied at gate `6610664`; org rulesets off |

**A policy change:** edit `config/<area>.toml`, open a PR (CI runs
`qqcfg validate`), merge, deliver any changed workflows with
`qqcfg deliver <repo>`, and bump each tool's infra-config pin so it sees the
change.

**Rules config cannot loosen:** stable promotion needs the policy-owner;
canary is agents-only; agents may land alone only clean reverts, dependency
rolls and docs (none does in v0); at most 10 auto-reverts per 24 hours;
builders that run PR code get no secrets; repos are public only.

**Owners.** suraj is the policy-owner and owner of the org and all 13 infra
repos. Review is advisory today: the `qq-main` ruleset requires 0 approvals.
The other config areas and the product repos have no owners yet.

Source: [v0 status report](2026-10-05-qq-v0-status.md), "Configuring policies
and owners" and "Owners and bots".

qq is built in three versions:

| | v0 | v1 (plan) | v2 (plan) |
|---|---|---|---|
| In short | a thin first version of every repo, end to end on GitHub | unattended canary, dev channel, fuzzing, flake handling | Launchpad, remote execution, perf bisection, stable channel |
| Work items | 51 | 45 | 25 |
| Status on 2026-10-05 | built; settings applied; exit test not passed yet | not started | not started |

**v0's exit test**, all five at once:

| # | Test | Status on 2026-10-05 |
|---|---|---|
| 1 | All 13 repos public, each with CODEOWNERS, a generated presubmit and a merge queue | Partly: infra repos' presubmits are still hand-written |
| 2 | Both product repos gated through shared adapters; a red PR is refused | Partly: builders run interim commands, not recipes; no red-PR refusal recorded |

## 8. Limits today

- **Linux x86_64 only** for fetched toolchains; Mac and ARM users bring their
  own at the pinned versions.
- **No `qq run` yet**; you start an app with its own command.
- **Only `qq` 0.1.0 exists**; no depot release tag has been cut.
- **CI does not use recipes yet**; the generated builders run interim
  commands.
- **Nothing lands on its own**; every revert and roll needs a person.
- **GitHub is the only backend**; Launchpad is v2.

Source: [v0 status report](2026-10-05-qq-v0-status.md), "Limitations".
