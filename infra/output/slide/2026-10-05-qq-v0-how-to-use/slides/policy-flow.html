POLICIES
How a policy change reaches a repo
1 · EDIT
Change config/<area>.toml in a PR. CI runs qqcfg validate: schemas, references, invariants, generated/ up to date.
2 · REVIEW
CODEOWNERS requests suraj's review on every policy path; advisory today (0 approvals required; GAT-03 not started). Squash-merge.
3 · DELIVER
qqcfg deliver <repo> <checkout> writes the workflows into a product-repo checkout, opened as a PR; drift checks fail hand edits.
4 · PIN BUMP
Each tool sees the change only after its own infra-config pin is bumped.
Repo settings are code too: edit gate's settings/github.toml, merge, then an org owner runs one command
( mkdir -p ~/qq-apply && cd ~/qq-apply && rm -rf qq-gate && git clone -q https://github.com/quirq-ai/gate qq-gate && cd ./qq-gate && git checkout -q <COMMIT> && scripts/apply.sh )
It shows a dry run, writes only what you approve at its prompts, and is safe to re-run. Replace <COMMIT> with the gate commit you are given; details in gate's docs/apply-settings.md.
