Report, 2026-10-05. Requested by suraj. It turns the phase part of the qq v0
one-pager and slide deck (shared on 2026-10-04) into a standing document,

## The question and the short answer

**What are qq's phases, what does each one deliver, how is each one tested,
and where does each stand today?**

qq is built in three versions. **v0** gives every one of the 13 infra repos a
thin first version of its job, end to end on GitHub. **v1** makes the daily
canary run unattended and adds the dev channel, fuzzing, flake handling and
failure tracking. **v2** adds Launchpad (quirq's own cloud) as a second
backend, remote execution, perf bisection and the stable channel.

- **v0 is built, and its repo settings are now applied, but its exit test has
  not passed yet.** The v0 code is merged in all 13 repos, the repo rulesets
  were applied, and both product repos run the generated builders. The live
  validations (a red PR refused, 7 unattended canaries, an automatic revert)
  have not run or are not recorded yet.
- **v1 and v2 are plans, not findings.** Nothing in them has started. They are
  described here from the version plans; every v1 and v2 statement below is a
  plan.

## How qq is laid out

qq is modelled on Chromium's infrastructure. infra-config's `config/org.toml`
names the Chromium counterpart of each of the 13 repos. This topic groups them
into four stages by where they act on a change (the grouping is this topic's;
each repo's role is from its README and `org.toml`).

| Stage | Repo | Its job | Chromium counterpart (from `org.toml`) |
|---|---|---|---|
| Your machine | depot | the `qq` command line | depot_tools |
| Your machine | sync | the manifest schema and its only parser | gclient, DEPS and gclient_eval |
| Your machine | recipes | one adapter per target kind | chromium/tools/build recipes and recipes-py |
| Your machine | toolchains | toolchains built, promoted and pinned by digest | CIPD, 3pp and the clang upload/promote flow |
| Your machine | remote-build | where actions run, and their cache | goma, reclient, Siso and RBE |
| Before landing | infra-config | all policy and builder definitions as data | infra/config with lucicfg; infradata/config |
| Before landing | gate | the required checks and the merge queue | LUCI CV and commit-queue.cfg |
| Before landing | test-pipelines | stored results, verdicts, failure records | ResultDB, ResultSink and LUCI Analysis |
| After landing | gardener | keeps `main` green: tree status, bisection, reverts | gardeners, Sheriff-o-Matic, LUCI Bisection, tree closers |
| After landing | rollers | keeps dependencies and toolchains current | Skia AutoRoll |
| After landing | perf | performance numbers per commit | chrome.perf, the perf dashboard and Pinpoint |
| Shipping | release | lkgr, channels, the daily canary, rollback | V8 release scripts and lkgr finder, chrome-official-brancher; LUCI promote.py |
| Shipping | installer | clients follow a channel instead of `main` | chrome/updater and chrome/tools/build/win |

Source: [infra-config `config/org.toml`](https://github.com/quirq-ai/infra-config/blob/310e3264f5de3cd9822b3a4712ae0a372b97dac3/config/org.toml).

## v0: a base version of every repo, end to end on GitHub

### Goal

From the plan: every one of the 13 infra repos exists, is public, sits behind
its own gate and does a first, thin version of its job. A change to a product
repo is built from its manifest, gated on the exact merge result, watched after
it lands, and shipped to the canary channel by agents every day.

### Scope rules

- Product kinds: the latest stable Python and Next.js only. Containers and
  docs-only kinds wait for v1.
- Public repos only. The first product repos are xo-space (`python-service`)
  and innernet (`node-app`).
- Execution on GitHub (merge queue and Actions), behind the executor
  interface so Launchpad can replace it later.
- Only the canary channel is live. Dev is declared but off; stable and the
  installer are priority P4 (low).

### What is in it

51 work items across org setup and every repo: 4 org, 4 depot, 4 sync,
5 recipes, 5 infra-config, 4 test-pipelines, 4 gate, 3 toolchains,
2 remote-build, 4 gardener, 2 rollers, 4 release, 2 installer, 2 perf and
2 product-repo onboardings. In short, per repo:

| Repo | v0 delivers |
|---|---|
| org | the 13 repos; owners; merge queue and rulesets; the monthly compute ceiling |
| depot | `qq` with version pinning; `qq fetch` and `qq sync`; `qq build` and `qq test`; `qq upload`, `try`, `land`, `status` |
| sync | schema `quirq-repo/1`; the one parser and editor; the pin check; the "no other parser" check |
| recipes | the adapter contract and loader; `python-service`, `pytest` and `node-app` adapters; property tests; deploy to a canary test environment |
| infra-config | publish the config skeleton; generate every v0 builder; fill the stubs v0 needs; suraj's open values; one source for policy |

| gate | required checks from config; the agnosticism guard; the verification-surface rule; gate timing |

| rollers | the toolchain pin roller; Dependabot lockfile updates |
| release | `lkgr`; channel pointers and rollback; the daily canary; the daily canary report |
| installer (P4) | the channel manifest; xo-space test installs on canary |
| perf | the `bench` capability and storage; a build-size record |
| product repos | onboard xo-space and innernet |

## v1 (plan): unattended canary, dev channel, fuzzing and failure tracking

Everything in this section is a plan. None of it has started.

### Goal

The daily canary runs with nobody watching: it soaks, rolls itself back,
fuzzes, files its own failure records and drafts its own postmortems. The dev
channel opens with human approval. Results become trustworthy (flakes
handled), builds become hermetic and cached, and the gardener and rollers work
at full strength. Containers and docs-only repos join, and PostHog becomes a
canary health signal.

### What is in it

45 work items. The headline ones, by area:

| Area | v1 plans |
|---|---|
| org | one-command, fully idempotent setup whose only approvals happen on GitHub (added 2026-10-04 after the v0 apply) |
| depot | `qq roll`, `qq channel` (show, hold, release, roll back), `qq failure` and `qq postmortem` |
| sync | mirroring (builds pass with upstream registries blocked); schema `quirq-repo/1.1` with fuzz targets, probes and deploy targets |
| recipes | `container-image` and `static-docs` adapters; Python fuzzing (Atheris with ClusterFuzzLite), Node fuzzing (Jazzer.js) and API fuzzing (Schemathesis); real canary deploy targets |
| infra-config | dev channel on; health thresholds; fuzz schedules and filing caps; postmortem and recurrence policy; onboard docs, wiki and the container kind |
| test-pipelines | flake detection and quarantine with expiry; exoneration of known flakes; a flakiness check for new tests; failure classes and recurrence |
| gate | result reuse; the admission bar; tree status in the gate |
| toolchains | a reproducibility check; a container toolchain |
| remote-build | a shared REAPI cache for CI and laptops |
| gardener | test-failure reverts; revert precision; a postmortem drafting agent; canary bisection |
| rollers | weekly rolls for every pin with no human |
| release | canary soak and automatic rollback; a canary fuzz stage; the dev channel; escalation |
| installer (P4) | test installs follow dev |
| perf | trend and threshold alerts; a bundle-size budget |
| PostHog | fix the docs proxy; error tracking, alerts into failure records and feature flags on canary |
| product repos | onboard docs and wiki |

### Exit test (plan)

1. 14 green daily canaries in a row with zero human touches.
2. A planted bad canary that passes CI but fails after deploy is rolled back
   automatically within the soak window, with a failure record linked to
   culprit and fix, and a postmortem draft whose every claim cites a run,
   result or commit.
3. A planted fuzz crash becomes one deduplicated issue with a reproducer, and
   the issue closes only when the daily replay passes after the fix.
4. Dev has been promoted 4 times, each by a human owner approving an agent's
   evidence.
5. A failure class seen twice in 14 days has produced a new test, fuzz target
   or gate.
6. Flake rate is reported weekly, the cache hit rate on unchanged inputs is at
   least 90%, and `main` is red under 60 minutes a week for 4 weeks.

## v2 (plan): stable, speed, depth and Launchpad

Everything in this section is a plan. None of it has started.

### Goal

Everything v1 runs on GitHub can also run on Launchpad, quirq's own cloud.
Remote execution and perf detection reach Chromium's shape. Fuzzing gains
depth. Stable promotion and installers that follow channels arrive at
priority P4 (low), so they may trail the rest. Agents hold the gardener,
roller and release rotations.

### What is in it

25 work items, deliberately coarser than v0's. The headline ones:

| Area | v2 plans |
|---|---|
| Launchpad | Launchpad behind the existing backend seam (`backend = "launchpad"`); a gate queue that does not need GitHub's merge queue |
| depot | `qq try` and `qq land` on either backend |
| sync | schema `quirq-repo/2`: go and rust kinds, cross-repo dependencies |
| recipes | go and rust adapters; Launchpad deploy targets |
| infra-config | stable channel on (P4); autonomy raised or lowered by scorecard rules |
| test-pipelines | failure-cluster bug policies; autosharding |
| gate | cross-repo gating |
| toolchains | revisit the transport (OCI images today) |
| remote-build | remote execution with Buildbarn; autoscaled worker pools |
| gardener | agents hold the rotation |
| rollers | cross-repo rolls with canary feedback |
| release | stable promotion, staged rollout and a stable rollback drill (P4) |
| installer | xo-space's installer and updater follow a channel; a desktop updater evaluation (P4) |
| perf | perf bisection; latency budgets |
| fuzzing | coverage-guided depth; a self-hosted fuzzing backend evaluation |

### Exit test (plan)

1. The same build runs on the `github` and `launchpad` backends with matching
   output digests for deterministic targets, chosen only by the `backend`
   field in infra-config.
2. Gate p50 under 10 minutes and p90 under 20 minutes for 4 weeks.
3. A planted 10% perf regression is alerted and bisected to its culprit.
4. 8 weeks with the intervention rate under suraj's target, a revert rate no
   worse than v1, and no policy-path change landed without owner approval.
5. Priority P4, may trail: one stable promotion by suraj with accurate notes,
   a rollback drill under 10 minutes, and xo-space's installer and updater
   following a channel instead of `main`.

### Status

Not started. (Inference: it follows v1.)
